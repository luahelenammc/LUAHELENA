## 1. Mother law and core sentence

> **Executor completion is not cycle completion. Execution returns; Chat closes the loop.**

The stable sentence is:

> **Chat understands and decides. Work produces. Codex builds. Chat accepts and integrates.**

This is a routing and closure protocol. It does not grant permissions, invent unavailable tools, guarantee a model result, or turn a surface label into a capability that the current environment does not expose.

A task is not complete merely because a surface produced text, a tool returned success, a file was created, a repository accepted a commit, or a model stopped generating. Completion requires a verified delta, an explicit acceptance state and a truthful claim ceiling.

## 2. The tri-surface model

Chat, Work and Codex are specialized execution surfaces with different native strengths. They are not three ranks in a prestige ladder and they are not interchangeable names for the same runtime.

### Chat

Chat owns understanding, judgment, clarification, comparison, architecture, bounded correction, acceptance and integration. It is the sovereign surface for deciding what should happen and whether the returned evidence supports closure.

Chat may perform a direct mutation when the required action is available and the mutation is bounded, legible and materially within conversational scope. The surface boundary is about object geometry and available action, not about a slogan.

### Work

Work owns sustained execution over knowledge artifacts and office-style deliverables: long research, multi-file documents, connector-mediated source operations, structured reports and final artifacts. Work is appropriate when continuity, context locality, multi-step persistence or artifact production is loadbearing.

Work does not own every task containing a document. A short decision, a bounded edit or a repository mutation can belong elsewhere.

### Codex

Codex owns executable systems: repositories, code, tests, builds, terminals, runtime behavior, refactors, migrations, debugging and other mutations whose sovereign object is an executable or source-controlled system.

Codex is first-class in the public routing model. When an operation requires repository inspection, code mutation, test execution or runtime evidence, the route must name Codex when that surface is available. A document about code is not automatically a Codex task; a code change is not merely a Work task because it produces a file.

### The cycle

The preferred route is:

**Chat → Work → Codex → Chat**

The route is not mandatory. It is a useful closed loop when a knowledge artifact must be prepared, an executable system must be built or tested, and Chat must independently accept the resulting evidence. A task can start and finish in Chat, move directly from Chat to Codex, use Work without Codex, or stop at a user decision.

## 3. Route by object geometry

Route the sovereign object, not the most visible noun in the request.

| Object or responsibility | Sovereign surface |
|---|---|
| Meaning, judgment, architecture, comparison, clarification or bounded correction | Chat |
| Knowledge artifact, document, research body, office file, connector operation or final report | Work |
| Repository, code, test, build, terminal, runtime, executable system or code migration | Codex |
| Acceptance, claim ceiling, residual classification and final integration | Chat |

When several objects are present, decompose the task into explicit stages and name each stage’s owner. Do not silently make one surface responsible for an object it cannot verify.

## 4. Six routing dimensions

A sound route records six independent dimensions.

### 4.1 Object geometry

What is being changed or decided? Name the sovereign object and the observable delta.

### 4.2 Execution surface and harness

Where will the operation actually run? Record the available connector, terminal, repository, document surface, browser, native skill or other harness. Surface availability is an environmental fact, not an assumption.

### 4.3 Capability tier and model

Choose the capability tier separately from the surface. The stable qualitative tiers are:

- **efficient:** clear, bounded, repeatable work
- **balanced:** ordinary multi-step work with moderate ambiguity
- **strong:** difficult synthesis, architecture, debugging or high-consequence judgment
- **frontier:** work whose material value depends on the strongest available reasoning and whose budget can support it

A surface, model family, plan, speed mode or label does not by itself prove a tier. Route by demonstrated availability and observed fit.

### 4.4 Reasoning effort

Reasoning effort is an independent control. Lower effort can favor speed and lower token use; higher effort can favor deeper analysis and may cost more time or allowance. Choose the lowest effort that can safely resolve the task, then raise it only when ambiguity, coupling, risk or verification demands it.

Do not use model strength as a substitute for missing evidence, missing permissions, unavailable tools or an incoherent specification.

### 4.5 Continuity and locality

Ask whether the work must persist across many steps, files or returns; whether the context must remain local to a specialized surface; and whether a handoff, checkpoint or receipt must survive interruption.

Continuity is loadbearing when losing state would materially change the result or make recovery ambiguous. Otherwise, keep the operation smaller and local.

### 4.6 Execution envelope

Record the envelope that can change the outcome: input allowance, output allowance, tool availability, connector permissions, fanout, tests, time, checkpoints, reversibility, user decisions and fallback routes.

A route is not ready because the destination has a good name. It is ready when the envelope can carry the work and return evidence.

## 5. Availability before escalation

Before changing model, effort or surface, test the actual failure boundary.

Record, as applicable:

- whether the requested surface is available in this client and plan;
- whether the needed connector, repository, document or terminal is reachable;
- whether the current identity has the required read or mutation permission;
- whether the file or repository state can be refreshed;
- whether the requested operation is native to the harness;
- whether the result can be verified independently;
- whether the fallback surface can own the same sovereign object.

Classify an unavailable route as a routing or environment condition. Do not describe a missing connector as a weak model, a failed permission as a reasoning failure, or a budget stop as evidence that the task was impossible.

If a route is unavailable, use the smallest valid reroute, downshift, phase boundary or user decision. Preserve the original objective and claim ceiling.

## 6. Budget Survivability Gate

Run a qualitative Budget Survivability Gate before sustained expensive execution, high-effort reasoning, frontier work or large fanout.

The gate considers:

- available allowance and current budget risk;
- selected surface, model tier and reasoning effort;
- input and output size;
- number and cost of tool calls;
- fanout and parallel branches;
- tests, verification and readback;
- checkpoint frequency and recoverability;
- likely retries and fallback routes;
- the material gain expected from the chosen route.

The gate returns one of these explicit outcomes:

- **PASS_DIRECT** — the work fits as one bounded run;
- **PASS_PHASED** — execute with checkpoints and phase boundaries;
- **PASS_FRONTIER_BURST** — reserve the strongest route for a narrow high-value slice;
- **DOWNROUTE_MODEL_OR_EFFORT** — keep the surface and lower the capability or effort;
- **COMPRESS_CONTEXT_FIRST** — reduce the input before execution;
- **REDUCE_TOOL_OR_FANOUT** — narrow calls, branches or retrieval;
- **WAIT_OR_REQUIRE_ADDITIONAL_ALLOWANCE** — do not begin an execution that cannot survive;
- **REROUTE_SURFACE** — the current surface cannot carry the object or envelope;
- **BLOCKED_RESOURCE_CONDITION** — an external permission, connector, file, repository or runtime condition prevents a truthful run.

This gate is qualitative by design. Do not invent a universal percentage, token tariff or performance ratio. Reassess after a large context load, material failure, frontier burst, tool expansion or return with incomplete evidence.

## 7. Context Diet

Context is a budgeted instrument, not a virtue measured by volume. Load the smallest set that can establish authority, objective, baseline, constraints, evidence and acceptance.

The main failure modes are:

- **starvation:** a required source, constraint or receipt is absent;
- **distraction:** low-value material consumes attention and allowance;
- **clashing:** competing instructions or authorities remain unresolved;
- **fossilization:** stale facts continue to govern;
- **duplication:** repeated copies create apparent support without new evidence.

A practical context diet is progressive:

1. identify the sovereign object and current authority;
2. load the minimum relevant kernel, source or repository instructions;
3. retrieve targeted evidence and inspect the real state;
4. execute the smallest reversible or checkpointed delta;
5. load more only when a named uncertainty requires it;
6. return a receipt containing what changed, what was tested and what remains.

Compression must preserve authority, decisions, constraints, failure state, evidence and next action. A shorter context that deletes these items is not a diet; it is starvation.

## 8. Surface gates

### Chat gate

Keep the task in Chat when the sovereign work is understanding, decision, comparison, clarification, architecture, bounded correction or acceptance and the required action is available.

A Chat handoff must not conceal a missing fact, unresolved user decision or unsupported claim. If a direct answer would materially depend on live state, route to the source-bearing surface and return evidence.

### Work gate

Route to Work when the sovereign work is long research, multi-file knowledge production, connector-mediated document work, structured office artifacts or sustained execution whose continuity is loadbearing.

A Work handoff must state the current baseline, authoritative sources, exact delivery, verification rule, allowed mutation and return contract. “Do research” or “make the document better” is not a ready handoff.

### Codex gate

Route to Codex when the sovereign work is repository mutation, code creation or editing, test/build execution, runtime diagnosis, refactor, migration, terminal operation or executable-system verification.

Codex must inspect the repository’s local constitution before mutation. If an AGENTS.md or equivalent instruction file exists at repository or parent scope, read the applicable instructions and treat them as part of the execution envelope. The repository’s tests, build scripts and runtime evidence outrank a confident narration.

### Model and effort gate

After choosing the surface, choose capability tier and effort independently. If the problem is specification, authority, availability, context, workflow or budget failure, fix that dimension before paying for a stronger model.

## 9. Codex constitution and native parallelism

### Repository Constitution Law

For a repository task, the governing local instructions, contribution rules, generated-file boundaries, test commands, licensing rules and deployment constraints are part of the source of truth.

Codex should:

1. locate and read applicable AGENTS.md or equivalent repository instructions;
2. inspect the relevant code, tests, configuration and existing implementation;
3. identify the smallest ownership boundary for the requested change;
4. preserve unrelated user changes and do not rewrite history casually;
5. run the narrowest relevant tests, then broader verification when risk warrants it;
6. report what was actually changed and verified.

No instruction file is not permission to improvise broad architecture. It means the agent must use the repository’s visible evidence and keep the mutation bounded.

### Native Parallelism Gate

Logical plurality is not physical subagents.

Parallel execution is justified only when the work has separable ownership, a shared baseline, no conflicting writes, a clear convergence step and a verification plan. More agents can increase coordination, merge, context and budget cost. Use one execution when decomposition does not create material independent progress.

Every parallel branch returns its own scope, evidence, failure class, changed files and unresolved delta. The integrator remains responsible for convergence and Chat remains responsible for acceptance.

## 10. Capability economics and frontier control

### Dated calibration

As a qualitative calibration recorded on 2026-09-06, the working tiers are:

| Tier | Illustrative model route |
|---|---|
| efficient | Luna |
| balanced | Terra |
| strong | Sol |
| frontier | Astra |

This table is a dated operating calibration, not a universal benchmark, price list, plan guarantee or fixed capability ranking. Product availability, model names, limits, speed modes, context windows and usage behavior can change. Work and Codex may draw from shared usage in the current product configuration, but the actual allowance depends on the current product, model, effort, context, output, tools and fanout. Recheck official sources before making a volatile product claim.

### Frontier ROI Gate

Use frontier capability only when the expected material gain justifies its allowance and verification cost. Ask:

- Is the task genuinely ambiguous, coupled, high-consequence or frontier-sensitive?
- Can decomposition isolate a small high-value slice?
- Would a strong route solve the real bottleneck, or only make a bad specification more elaborate?
- Is there a checkpoint before irreversible or expensive work?
- Can the result be verified by evidence independent of confidence?
- Is the fallback still useful if the burst stops early?

### Frontier Burst

Prefer a narrow Frontier Burst for the hardest judgment, architecture choice, failure diagnosis or quality-critical slice when the whole run does not need frontier capability.

A Full Run is justified only when decomposition is impossible or would destroy the required coherence, the Budget Survivability Gate passes, the expected material gain is real, and checkpoints and verification are explicit.

### Product calibration boundary

Official product documentation can support current product facts; it does not by itself validate this protocol’s architecture. Do not promote an anecdotal limit, speed observation, model label or usage ratio into a permanent law. This portable keeps the stable geometry above volatile product calibration.

Useful calibration sources include [OpenAI pricing and usage](https://learn.chatgpt.com/docs/pricing), [OpenAI model guidance](https://learn.chatgpt.com/docs/models), [reasoning guidance](https://developers.openai.com/api/docs/guides/reasoning), [Codex CLI](https://learn.chatgpt.com/docs/codex/cli), [AGENTS.md guidance](https://learn.chatgpt.com/docs/agent-configuration/agents-md) and [best practices](https://learn.chatgpt.com/guides/best-practices).

## 11. Executor Readiness Gate

Use this executor-neutral gate for Chat, Work or Codex.

A ready handoff contains:

- **identity:** task name, owner, date and current status;
- **objective:** the user-visible outcome;
- **sovereign object:** what must change or be decided;
- **baseline:** current source, repository, document, branch, revision, file set or prior receipt;
- **authority:** sources that govern and sources that are evidence only;
- **route:** selected surface, capability tier and reasoning effort, with the reason;
- **execution envelope:** permissions, tools, budget outcome, context diet, fanout, checkpoints, reversibility and fallback;
- **delivery:** exact files, fields, sections, outputs or tests expected;
- **return:** receipt fields, readback, acceptance state and residual routing.

If one of these is unknown, name the unknown and either ask a targeted question, perform reconnaissance or record a blocked condition. Do not fill a missing authority with a plausible guess.

## 13. Executor Return Contract

Every executor returns a compact evidence-bearing receipt:

- **scope:** what it was asked to do;
- **baseline:** what it actually inspected;
- **delta:** exact files, fields, commits, revisions or outputs changed;
- **evidence:** tests, readback, links, hashes, screenshots or other verification;
- **failures:** what failed and its classified domain;
- **residuals:** what remains and why;
- **claim ceiling:** what the receipt supports and what it does not;
- **next route:** Chat acceptance, user decision, bounded repair or new execution;
- **new_execution_required:** false, true, or partial with the irreducible delta named.

A successful tool response is evidence about that tool response, not proof that the requested objective is complete.

Historical V2 and V3 return receipts remain valid lineage records. Their field names and semantics must not be silently rewritten; the executor-neutral V4 names govern new handoffs.

## 14. Chat Postflight

Chat Postflight is mandatory after an executor returns.

### 14.1 Refresh the real state

Read the current source, document, repository, branch, generated artifact or deployment state independently of the executor’s narrative. Capture the current revision, commit, file hash or equivalent receipt.

### 14.2 Audit claim against evidence

Compare the requested delivery with the observed delta. Check that the authoritative source changed, the intended files are current, tests/readback actually ran, links and generated outputs resolve, and no unsupported product or completion claim slipped into the result.

### 14.3 Classify residuals

For every open item, classify it as:

- **none:** no material delta remains;
- **bounded Chat repair:** Chat can correct it within available scope;
- **new execution required:** another surface must perform an irreducible delta;
- **user decision required:** authority, preference, disclosure or scope is missing;
- **blocked external condition:** permission, connector, resource or environment is unavailable;
- **optional next step:** useful but not required for the stated objective.

Do not create a new execution merely because an executor returned a generic suggestion. Create it only for a verified unresolved delta.

### 14.4 Close or re-enter

Chat applies bounded repairs when authorized and verifiable. It creates a new handoff only for the remaining irreducible delta, with the delta named in the field new_execution_required. It then records an explicit acceptance state and claim ceiling.

The closed loop is:

1. executor returns;
2. Chat refreshes real state;
3. Chat audits evidence;
4. Chat repairs bounded issues or classifies residuals;
5. Chat accepts, requests a user decision or opens a delta-only execution;
6. Chat integrates the result into the governing source.

## 15. Acceptance states

Use explicit states:

- **ACCEPTED** — requested objective is verified and no material residual remains;
- **ACCEPTED_WITH_RESIDUALS** — objective is verified; named residuals are non-blocking and within the claim ceiling;
- **PARTIAL_NEW_EXECUTION_REQUIRED** — only a named irreducible delta remains;
- **USER_DECISION_REQUIRED** — a human choice or authority is necessary before truthful completion;
- **BLOCKED_EXTERNAL_CONDITION** — the environment prevents the required read, write or verification;
- **NO_DELTA** — the requested change was already present or the source was not materially changed, with evidence recorded.

Acceptance is not a mood, a model confidence score or a green tool response.

## 16. Phased execution

For complex work, use four execution phases and one closure phase.

### Phase 0 — Reconnaissance

Read the relevant instructions, source, repository state, connectors, current revisions and existing implementation. Identify authority, object geometry, risks, availability and the smallest useful route.

### Phase 1 — Hard judgment

Resolve scope, supersession, ownership, architecture, route, capability tier, effort, budget outcome, checkpoints and acceptance rules before broad mutation.

### Phase 2 — Bounded mutation

Change only the authorized source and dependent surfaces. Preserve unrelated material. Keep commits, edits or artifact writes legible and recoverable.

### Phase 3 — Verification

Run tests, validators, readback, link checks, hash checks, build checks or runtime checks appropriate to the object. Record failures rather than smoothing them into prose.

### Phase 4 — Chat Postflight

Refresh the real state independently, audit the return contract, classify residuals, apply bounded repairs, accept or re-enter, and update the governing source.

The phases can collapse for a tiny task, but the responsibilities do not disappear.

## 17. Failure domains and salvage

Classify failure before selecting a stronger route:

- **specification:** objective, scope or acceptance is incoherent;
- **source/authority:** wrong, stale, competing or missing authority;
- **routing:** surface or harness does not own the sovereign object;
- **tool/environment:** connector, permission, runtime or external resource failed;
- **context:** starvation, distraction, clashing, fossilization or duplication;
- **workflow/fanout:** sequencing, ownership, convergence or parallelism failed;
- **budget/resource:** allowance, time, output, tool cost or checkpoint envelope failed;
- **cognitive:** reasoning, synthesis, implementation or verification quality failed.

### Salvage before retry

When execution stops or returns incomplete:

1. inspect surviving artifacts, receipts, diffs, revisions, logs and partial outputs;
2. identify the last verified state;
3. separate unavailable private reasoning from observable evidence;
4. reconstruct only the missing delta, not the entire run;
5. reroute, downshift, compress context, reduce tools/fanout or ask for a decision;
6. record a Budget Incident Receipt when budget or allowance materially shaped the outcome.

Do not claim to have recovered hidden reasoning that is not available. Preserve evidence and rebuild the smallest auditable continuation.

### Budget Incident Receipt

- task and phase;
- route, model tier and effort;
- observed stop or degradation;
- allowance/context/tool condition;
- last verified artifact or revision;
- salvageable delta;
- new route or fallback;
- residual claim ceiling.

## 18. Frontier, fallback and residue routing

The preferred fallback order is:

1. preserve the objective and authority;
2. compress context without deleting loadbearing facts;
3. reduce tool calls or physical fanout;
4. lower effort or capability tier when the bottleneck is not reasoning;
5. phase the run with checkpoints;
6. reroute to the surface that owns the sovereign object;
7. request a user decision or additional allowance;
8. stop with a truthful blocked receipt.

The smallest unresolved delta determines re-entry. Route a document delta to Work, a repository/test/runtime delta to Codex, and a meaning/authority/acceptance delta to Chat. Do not reopen a completed stage to make the receipt look more complete.

## 20. Handoff schema

The minimal V4 schema is:

1. **identity** — who/what/when/status;
2. **objective** — user-visible outcome and acceptance;
3. **sovereign object** — the object that owns the delta;
4. **baseline** — current revision and existing implementation;
5. **authority** — governing versus evidence-only sources;
6. **route** — surface, capability tier and effort;
7. **execution envelope** — tools, permissions, budget, context, fanout, checkpoints and fallback;
8. **delivery** — exact outputs and verification;
9. **return** — receipt, residuals, acceptance and new_execution_required.

This schema is deliberately portable across Chat, Work and Codex. The word Work may remain in historical receipt names, but new V4 handoffs use executor-neutral fields.

## 21. Safe operating rules

- Read before mutation; refresh before claiming current state.
- Separate object geometry from execution surface.
- Separate model capability from reasoning effort.
- Treat connector access as access, not authority.
- Prefer the smallest sufficient context and the smallest reversible delta.
- Preserve user decisions, provenance, lineage and claim ceilings.
- Keep current and historical generations distinct.
- Use tests, hashes, readback and runtime evidence where they exist.
- Report blocked conditions plainly.
- Never turn a tool response into a universal completion claim.
- Never silently convert anecdotes into pricing, usage or performance laws.
- Never create physical fanout without an ownership and convergence plan.
- Never ask an executor to own a delta another surface must verify.
